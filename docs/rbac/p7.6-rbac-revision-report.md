# P7.6 RBAC revision report

Catalog version: `2.0.0`  
Scope: canonical design artifacts only; no runtime or database authority change.

## Approved interpretation

Rental Operations is a multi-role assignment of `dispatcher` + `equipment-coordinator` + `operations-manager`, not another broad role. Management receives `management-viewer` + `read-only-auditor`. This preserves the approved Permission → Role → User hierarchy and avoids direct user permissions.

## Permission changes

### Added

- Dashboard split: `dashboard.executive.read`, `dashboard.financial.read`.
- User administration: `users.access.reset`, `users.auditHistory.read`, `users.effectivePermissions.read`.
- Role administration: `roles.create`, `roles.clone`, `roles.compare`, `roles.assignedUsers.read`.
- Permission administration: `permissions.catalog.read`, `permissions.catalog.manage`.
- Permission display groups and nine auditable configuration sections.

### Removed from roles

- Billing Officer: billing/collection approve, close, delete, reopen, finalization, invoice issue/void, and collection reversal.
- Management Viewer: all transaction actions, administrative metadata, and broad record exports; only approved report/dashboard export remains.
- Operator: dashboards, other operators, Rentals, maintenance, projects, master data, reports, and non-owned records.
- Maintenance Staff: Rental/assignment/customer/operator/project management, billing, settings, destructive deletion, and general exports.
- Dispatcher and Equipment Coordinator: operational approval and unrelated export authority.
- Operations Manager: operational record creation/update, settings mutation, user reads, and financial approval/export.

### Split

- Billing Staff → Billing Officer with preparation/monitoring separated from approval and reversal.
- Read-Only Auditor → Management Viewer plus Auditor.
- Rental Operations → Dispatcher + Equipment Coordinator + Operations Manager.
- Generic dashboard read → executive and financial dashboard reads.
- User/role administration → explicit read, assign, clone, compare, audit, reset, and catalog actions.

### Kept

- Nine protected canonical roles, multi-role union semantics, tenant scope, deny-by-default, alias/deprecation support, and role-derived permissions only.
- Standard read/create/update/delete/approve/close/export decomposition and workflow-specific actions.

## Role overlap analysis

- Management Viewer is wholly contained in Auditor (16 shared permissions). This is intentional only when both responsibilities are assigned; future enforcement should avoid redundant display while retaining separate business meaning.
- Dispatcher and Equipment Coordinator share 12 read/coordination permissions; their write authorities remain distinct.
- The Rental Operations composition contains 47 unique permissions, not the arithmetic sum, because overlaps are deduplicated.
- Billing Officer shares ten read/report permissions with Management Viewer/Auditor but retains financial writes; Management roles retain none.
- Operator overlaps only on three scoped reads with operational roles; scope rules make these own-record permissions, not tenant-wide duplicates.

## Duplicate authority analysis

- No permission is assigned directly to a user.
- Multi-role unions must deduplicate permission codes deterministically.
- No non-administrator role has `allPermissions`.
- No operational role contains billing mutation authority.
- Only Operations Manager contains Rental/DEUR operational decision authority.
- Management Viewer and Auditor overlap intentionally; assigning both must not generate duplicate grants or audit events.

## Administration readiness

- User administration is role-based: create, activate/deactivate, assign multiple roles, link Operator, view effective permissions, reset access, and view audit history.
- Normal user administration does not require permission-catalog mutation because role assignment and permission management are separate codes.
- Role create/clone/compare/assigned-user inspection are explicit.
- Custom roles are supported while canonical roles remain protected.
- Permissions are grouped into ten business modules rather than rendered as one flat catalog.
- Configuration is separated into General, Numbering, Rental, DEUR, Billing, Notifications, Scheduler, Security, and Integrations; all changes require audit records.

## Remaining gaps

1. Configuration permissions are still represented partly through generic `settings.*`; a later design should split all nine configuration sections into explicit read/update codes before enforcement.
2. Billing invoice export and Auditor authorization-metadata visibility need procedural confirmation.
3. Rental Operations approval actor separation must be defined when one user holds all three roles.
4. The P7.5 runtime comparison service remains pinned to the version 1 role names and must be revised only in a later implementation phase.
5. Database catalog version 1.0.0 remains unchanged; version 2.0.0 requires a future additive migration after approval.

## Determinism

All role codes, permission codes, group codes, grants, and scope rules are explicit and sorted during validation. Effective permissions are set unions keyed by permission code. Unknown roles and permissions remain denied.
