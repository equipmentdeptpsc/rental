# Supabase Migration Workflow

The authoritative SQL source is `database/postgresql/001_*.sql` onward. Files under `supabase/migrations` are generated byte-for-byte deployment mirrors and must never be edited manually.

Run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/sync-supabase-migrations.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/sync-supabase-migrations.ps1 -Check
npx supabase migration list --linked
npx supabase db push --linked --dry-run
npx supabase db push --linked
```

The synchronization script owns the timestamp mapping and rejects unexpected generated SQL or checksum differences. Supabase applies filenames in timestamp order corresponding exactly to the canonical numeric order. Remote state lives in `supabase_migrations.schema_migrations`.

Phase 11B added 008 for Equipment Status RLS/minimum grants, 009 for conditional Supabase Data API schema exposure, and 010 for conditional PostgREST cache reload. The latter two no-op on ordinary PostgreSQL where the `authenticator` role does not exist.

For failures, capture the hosted error, fix only the canonical migration, regenerate and verify the mirror, then reset only an approved disposable project or repair migration history when the schema and history are demonstrably mismatched. Never apply untracked dashboard changes or edit generated copies. Docker-based `db pull/reset` is optional for this new linked project and was not used in Phase 11A.
